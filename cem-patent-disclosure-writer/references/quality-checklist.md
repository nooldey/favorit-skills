# 专利交底书质量检查清单

交付前逐项检查。若不满足，应在文档中标注 `【待确认】` 或向用户追问。

## 一、结构完整性

- [ ] 是否包含八章：发明名称、背景、内容、附图、应用领域、具体实施方式、引证资料、其它说明。
- [ ] 如生成核心代码片段附录，是否作为专利附录而非软著代码材料。
- [ ] “发明内容”是否包含技术问题、技术方案、有益效果。
- [ ] 「六、具体实施方式」是否能对应「四、说明书附图」。
- [ ] 软件工程类方案的典型应用案例是否按“项目背景 → 技术挑战 → 解决方案实施 → 实施效果 → 具体应用场景 → 技术价值体现”展开。
- [ ] 是否保留签名、日期、技术交底人、联系方式占位。

## 二、技术事实

- [ ] 是否只把已知/可验证信息写成确定事实。
- [ ] 未确认的信息是否用 `【待确认】` 标出。
- [ ] 是否避免编造性能数据、用户数据、上线效果。
- [ ] 是否脱敏客户、项目、人员、内部系统名称。
- [ ] 是否排除密钥、访问令牌、内部域名、客户数据等不宜公开内容。

## 三、专利表达

- [ ] 是否突出技术方案，而非单纯业务流程或管理制度。
- [ ] 是否写清输入、处理、判断、输出。
- [ ] 是否写清模块、数据结构、流程、算法或规则。
- [ ] 是否避免“好用、先进、智能”等空泛评价。
- [ ] 是否避免无依据的绝对化表达，如“首创”“唯一”“完全解决”。
- [ ] 是否未混入软件著作权申请表、操作手册、前后 30 页代码材料等软著规则。

## 四、创新点与效果对应

- [ ] 每个创新点是否有具体技术特征支撑。
- [ ] 每个有益效果是否能从技术方案直接推出。
- [ ] 是否区分“业务收益”和“技术效果”。
- [ ] 是否说明新增不可缺少步骤产生的直接效果。

## 五、软件类充分公开

- [ ] 是否描述软件执行步骤。
- [ ] 是否给出关键数据结构或字段示例。
- [ ] 是否说明异常处理、重试、回滚、降级或日志机制。
- [ ] 如涉及算法，是否描述输入、输出、核心逻辑和终止条件。
- [ ] 如涉及 AI，是否说明数据来源、提示词/规则、模型输出校验或人工确认机制。

## 六、核心代码片段附录

- [ ] 代码片段是否来自真实项目源码，未由 AI 编造。
- [ ] 是否只选能支撑发明点的核心流程、算法、数据结构或异常处理代码。
- [ ] 是否记录文件路径、行号范围、选择理由和对应发明点。
- [ ] 是否排除无关样板代码、构建产物、依赖声明、测试数据。
- [ ] 是否完成敏感信息脱敏，并确认脱敏后仍能说明技术方案。

## 七、附图检查

- [ ] 是否建议至少 3 张核心附图。
- [ ] 图号是否连续。
- [ ] 每张图是否有图名和说明。
- [ ] 是否覆盖系统结构、核心流程、数据结构、异常流程中的关键项。
- [ ] 文中实施方式是否引用并解释附图。
- [ ] 截图类附图是否清晰、无水印、白底；不合格的是否标注 `【待处理】`。
- [ ] 正式提交结构是否可对齐 [`template-and-examples.md`](template-and-examples.md)「官方模板」八章与各章提示语。

## 八、可读性

- [ ] 章节编号是否清晰。
- [ ] 长段落是否拆分为编号列表。
- [ ] 术语是否前后一致。
- [ ] 是否保留必要的代码/伪代码/JSON 示例。
- [ ] 是否便于专利代理人提炼权利要求。

## 九、交付说明

最终回复用户时简要说明：

- 使用了哪些输入资料；
- 生成/修改了哪个文件；
- 是否生成核心代码片段附录和追溯清单；
- 哪些信息仍待用户确认；
- 是否未运行格式转换或未写入在线文档，以及原因。
