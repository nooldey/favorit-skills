# 飞书项目回写 writeback

本文件定义修复完成后如何准备飞书项目评论或字段更新。回写必须先展示给用户并获得明确确认。

## 回写前置条件

必须全部满足：

1. 已确认工作项 URL/ID。
2. 已完成根因定位和代码修复。
3. 已按 `validation.md` 完成本地验证，或明确记录无法验证原因。
4. 已按 `review.md` 对每个有 diff 子仓完成 `code-review-expert` 评审并处理意见。
5. 已按 `git.md` 读取每个有 diff 子仓的当前分支。
6. 已向用户展示拟回写内容并获得明确确认。

## 回写渠道

严格遵守：`FeishuProjectMCP > Meegle CLI > lark-cli`。

Meegle CLI 补充工具链参考：`../cem-feishu-project-basic/guidance/meegle-cli-guide.md`。

三者均失败时，报告失败原因和可重试命令，不切换到浏览器 UI 手工读写工作项。

## 回写内容原则

- 简短、事实化、可验收。
- 只写问题原因、修复方案、验证结果、修复分支。
- 不写内部推理过程、无关代码细节、未确认猜测。
- 不包含敏感凭证、账号 token、内部日志隐私数据。
- 不声称未执行的验证已经通过。

## 回写模板

```markdown
### 问题原因

[说明根因、触发条件和影响范围。]

### 修复方案

[说明核心代码改动、兼容策略和关键边界处理。]

### 验证结果

[列出已执行验证；无法执行的验证说明原因。]

### Code Review

[列出每个有 diff 子仓的 code-review-expert 结论和处理情况。]

### 修复分支

[子 git 仓库名]：[当前分支名]
[子 git 仓库名]：[当前分支名]
```

## 对用户确认话术

```markdown
以下是拟回写到飞书项目的内容，请确认是否发布：

[回写内容]

确认后我再通过批准工具写入飞书项目。
```

只有用户明确表达“确认发布/同意回写/可以写入”等含义后，才能执行回写。

## 最终回复与回写状态

- 若用户尚未确认：最终回复写“已准备回写内容，等待确认”，不要说“已回写”。
- 若回写成功：记录使用的工具、工作项和成功结果。
- 若回写失败：记录工具、错误、已尝试次数和建议下一步。
