# CEM 前端 Mono 缺陷修复检查规则

本规则只用于 `cem-frontend-mono-debugger` 的 mono 缺陷排查、修复、验证和 `code-review-expert` 复核。若项目已有更具体的规范、lint、类型约束或组件约定，以项目内规范为准。

## 1. Mono 边界

- 识别受影响 package、应用入口、页面路由和依赖方向。
- 不跨 package 引入未公开内部文件；优先使用已有导出入口、shared utilities、hooks 和类型。
- 修改 shared package 时，检查已知调用方，不只验证当前 Bug 页面。
- 不新增循环依赖、重复工具函数或局部私有实现来绕过现有抽象。

## 2. React 修复门禁

- 保持单一可信状态来源，避免 props、store、form state、URL query 保存同一业务值但不同步。
- `useEffect` 依赖必须完整；异步 effect 要处理竞态、卸载、旧请求覆盖新请求和错误态。
- 不在 render 中执行副作用、发请求、写 store、改 URL 或触发表单提交。
- 列表渲染使用稳定业务 key；条件渲染覆盖 loading、empty、error、无权限和数据缺失。

## 3. 空值与历史数据兼容

- 接口、URL、localStorage、配置、表单和外部组件回调数据都按不可信输入处理。
- 访问嵌套字段前处理 `null`、`undefined`、空数组、空字符串、异常枚举、历史字段名和类型漂移。
- 不用宽泛的 `as any`、非空断言或类型强转绕过问题；需要收窄类型时优先写显式 guard 或复用已有 schema。
- 明确区分未填写、填写为空、字段不存在和接口返回异常。

## 4. 请求、缓存与性能

- 检查修复是否增加首屏请求、重复请求、级联请求或无界轮询。
- 搜索、筛选、输入联想、滚动加载等高频交互应复用项目既有 debounce、缓存或请求取消策略。
- 缓存 key 必须包含影响结果的业务参数、权限参数和分页参数。
- 不在大列表 render 中做昂贵格式化、深拷贝、排序、正则解析或复杂权限计算。

## 5. 表单重复提交门禁

- 提交按钮、快捷键提交、弹窗确认、批量操作和自动保存都必须具备重复提交门禁。
- 门禁状态覆盖请求发起到 settle 的完整周期，并处理成功、失败、取消、页面卸载和弹窗关闭。
- 表单校验要覆盖 UI 校验和提交前校验；不能只依赖 disabled 状态。
- 提交 payload 要过滤纯展示字段，并正确保留用户有意清空的字段。

## 6. 缺陷场景覆盖

- 至少检查：新数据、历史数据、空数据、无权限、只读、网络失败、接口慢返回、重复打开页面、刷新后恢复。
- 列表页缺陷覆盖分页、筛选、排序、搜索、批量操作和跨页状态。
- 详情页缺陷覆盖首次进入、刷新、切换记录、返回列表和从外链进入。
- 弹窗/抽屉缺陷覆盖打开、关闭、二次打开、提交中关闭、表单重置和父子组件数据同步。

## 7. 验证要求

- 优先运行最靠近改动的测试，再按影响范围运行 package 级 lint、typecheck 或 build。
- UI 行为修复需要本地浏览器验证关键路径，检查 Console、Network、DOM 状态和用户可见反馈。
- 无法运行某类验证时，记录原因、影响和建议补验命令。
- 验证命令必须真实执行后再声称通过；失败时区分已有失败与本次改动导致的失败。

## 8. code-review-expert 评审重点

调用 `code-review-expert` 时，把以下重点写入评审请求：

- 本次 diff 是否符合 mono package 边界和项目既有约定。
- React hooks、状态来源、异步请求和渲染逻辑是否符合最佳实践。
- 是否引入 JS 性能问题、重复请求、缓存污染或列表渲染退化。
- 是否遗漏测试、验证或关键边界场景。
- 是否存在空值兼容、历史数据兼容或类型收窄不足。
- 表单、弹窗、批量操作和提交入口是否具备重复提交门禁。

## 9. 飞书项目回写内容

回写内容保持简短、可验收，只包含修复结论信息。准备回写前，先读取本地 git 变更涉及的各个子 git 仓库名及当前分支名；涉及多个仓库时在 `修复分支` 下逐行列出。

```markdown
### 问题原因

[说明根因、触发条件和影响范围。]

### 修复方案

[说明核心代码改动、兼容策略和关键边界处理。]

### 修复分支

[子 git 仓库名]：[当前分支名]
[子 git 仓库名]：[当前分支名]
```
