# 强制代码评审 review

本文件定义 `code-review-expert` 的调用时机、粒度和处理要求。

## 调用时机

只有在完成以下步骤后才能调用评审：

1. 已完成代码修改。
2. 已在对应子仓完成至少一轮相关验证，或明确记录无法验证原因。
3. 已读取每个有 diff 子仓的变更文件、diff 摘要和当前分支。

未完成验证前，不要把评审当作替代验证。

## 调用粒度

- 每个有 diff 的子 git 仓库分别调用一次 `code-review-expert`。
- 评审工作目录必须是对应子仓，不是 mono 根仓。
- 多子仓变更不能合并成一次根仓评审。

## 评审请求必须包含

- 子仓名称、path、当前分支。
- 工作项 URL/ID 和问题摘要。
- 根因与修复方案。
- 变更文件列表和验证记录。
- 需要重点检查的规则：submodule 归属、mono package 边界、React hooks、状态来源、异步请求、JS 性能、缓存、空值兼容、历史数据兼容、表单重复提交、测试遗漏。

## 评审结果处理

对每条评审意见分类：

| 分类 | 处理 |
|---|---|
| 必须修复 | 修改代码并重跑相关验证 |
| 建议优化 | 判断收益与风险，采纳或说明不采纳原因 |
| 误报 | 用源码证据说明为什么不采纳 |
| 阻塞 | 记录阻塞条件，请用户或项目负责人补充 |

若根据评审继续修改代码，必须重新运行受影响验证；必要时再次调用 `code-review-expert`。

## 评审结论模板

```markdown
### code-review-expert 结果
| 子仓 | 结论 | 问题 | 处理 |
|---|---|---|---|
|  | 通过/需修改/阻塞 |  |  |
```

## 禁止事项

- 禁止只在 mono 根仓执行空 diff 评审。
- 禁止忽略评审问题直接输出完成。
- 禁止把未处理的高风险问题写成“后续优化”来规避修复。
