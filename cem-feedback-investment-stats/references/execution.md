# Feedback 综合回收与研发投入统计执行细则

## MCP 调用顺序

### 1. 视图数据

使用 `get_view_detail`：

```json
{
  "project_key": "cem",
  "view_id": "视图ID",
  "fields": ["_all"],
  "page_num": 1
}
```

如果用户提供的是 URL，直接传 `url`，让工具解析视图参数。需要完整结果时，从 `page_num=1` 开始递增，直到返回不足一页或没有更多数据。

如果 `get_view_detail` 报错，停止后续统计，输出报错的工具名、视图 URL/ID、字段参数和原始错误信息；不要改用其他视图、历史报告或本地缓存继续统计。

视图返回成功后先锁定 feedback 集合：

| 场景 | 处理 |
|---|---|
| 用户要求视图全量 | 视图返回的 feedback 全部纳入统计，不再按上线时间二次过滤 |
| 用户给定上线时间范围 | 按上线时间字段做闭区间筛选；字段缺失的 feedback 保留并在缺失记录中标注 |
| 视图分页 | 从第 1 页开始逐页取完；不得只取首页后生成报告 |
| 视图为空 | 输出空表和查询成功记录，不补历史数据 |

### 1.1 客户声音回收视图

当用户需要 feedback 回收情况或报告要求包含客户声音填写率时，额外获取已填写和未填写客户声音集合：

| 集合 | 默认视图 | view_id | 用途 |
|---|---|---|---|
| 已上线已填写客户声音 | `https://project.feishu.cn/cem/workObjectView/yt_user_feedback/JMqybKtDR?scope=workspaces&node=28720388` | `JMqybKtDR` | 统计已填写数量、客户声音内容和本周新增填写候选 |
| 已上线未填写客户声音 | `https://project.feishu.cn/cem/workObjectView/yt_user_feedback/QOIjVgcDg?scope=workspaces&node=28494009` | `QOIjVgcDg` | 统计未填写数量和按上线时间分层 |

处理规则：

- 用户提供独立回收视图时优先使用用户视图；未提供且明确需要全局已上线回收率时才使用默认视图。
- 独立回收视图只用于回收统计分母，不替代研发投入主视图；两个集合不一致时分别命名为“回收统计全集”和“投入统计全集”。
- 如果独立视图查询失败，不能用历史报告补齐；可退回主统计集合计算局部回收率，并在报错记录说明覆盖范围变化。

### 2. 字段配置

查询 feedback 字段：

```json
{
  "project_key": "cem",
  "work_item_type": "yt_user_feedback",
  "field_query": "开发上线时间",
  "page_num": 1
}
```

客户声音字段同样需要查询：

```json
{
  "project_key": "cem",
  "work_item_type": "yt_user_feedback",
  "field_query": "客户声音",
  "page_num": 1
}
```

常见字段：

| 语义 | 常见字段名 | 常见字段 key |
|---|---|---|
| 开发上线时间 | 开发上线时间 | `field_d7593a` |
| 客户声音 | 客户声音 | `field_57aa16` |

不要硬编码字段 key；常见字段只作为匹配失败时的提示。

当前固定口径下，如果视图结果已直接返回以下字段，可以直接使用，不需要每次查询字段配置：

| 语义 | 固定字段 |
|---|---|
| Feedback 关联 Story | `field_255b77`、`field_b70230` |
| Task 关联 Story | `field_2c5aa5` |
| Task 预估耗时 | `field_fb844a` |
| Task 实际耗时 | `field_23cb2b` |
| Task 岗位分类 | `field_9a3d14` |

如果固定字段读取失败，必须记录失败字段；可以查询字段配置确认，但不能自行替换成语义相似字段后继续统计。

### 2.1 客户声音内容与新增填写

客户声音内容读取规则：

1. 优先使用视图返回的客户声音字段值。
2. 视图未返回客户声音但字段配置可用时，对单个 feedback 调用 `get_workitem_brief` 补齐。
3. 字段为空输出“未填写”；字段不存在输出“字段缺失”；内容较长也必须完整保留，不用省略号替代。

本周新增填写识别规则：

```json
{
  "project_key": "cem",
  "work_item_id": "feedback_id",
  "op_record_module": ["field_mod"],
  "operation_type": ["modify", "create"],
  "start": "本周一 00:00:00 的毫秒时间戳",
  "end": "统计日 23:59:59 的毫秒时间戳"
}
```

- 仅当操作记录命中客户声音字段 key 或字段名时，计入“本周新增填写”。
- 输出字段：Feedback ID、名称、客户声音完整内容、开发上线时间、填写时间、操作人（若返回）。
- 如果操作记录接口报错，保留已填写内容，不判定为本周新增，并把接口参数和错误写入“数据缺失与报错记录”。

### 2.2 未填写分层

仅对未填写客户声音集合分层：

| 层级 | 规则 |
|---|---|
| 超过 30 天 | 统计日 - 开发上线时间 > 30 天 |
| 15-30 天 | 15 天 <= 统计日 - 开发上线时间 <= 30 天 |
| 7-15 天 | 7 天 <= 统计日 - 开发上线时间 < 15 天 |
| 7 天内 | 统计日 - 开发上线时间 < 7 天，或上线时间缺失 |

如果配置 `exclude_deploy_before`，只从未填写分层统计中排除早于该日期的项；排除项数量、ID 和名称仍需在缺失与说明中可追溯。

### 3. feedback 到 Story

优先使用关联字段：

```json
{
  "project_key": "cem",
  "work_item_id": "feedback_id",
  "relation_field_key": "字段key",
  "page_num": 1,
  "page_size": 50
}
```

如果只有关系名，使用 MQL 高级语法。关系名以用户输入或字段配置为准，不要自行改写：

```sql
SELECT `工作项ID`, `名称`
FROM `cem`.`yt_user_feedback`
WHERE any_relation_match(relation('关系名'), x -> x.`工作项类型<target:all>` = 'story')
```

如果查询失败，只修正报错指出的字段或关系部分，不要大面积改写 MQL。

如果修正后仍失败，在报告中保留该 feedback 的视图数据，并把关联查询错误写入“数据缺失与报错记录”；不要根据名称相似度猜测 Story。

固定字段在视图结果中返回 Story 对象或 ID 时，直接解析为关联 Story；同一 feedback 的两个关联字段合并后按 Story ID 去重。

### 4. Story 下子 task

首选查询 Story 节点和子任务：

```json
{
  "project_key": "cem",
  "work_item_id": "story_id",
  "need_sub_task": true,
  "field_key_list": ["_all"]
}
```

如果子任务以计划表行存在：

```json
{
  "project_key": "cem",
  "work_item_id": "story_id",
  "row_field_list": ["base.*", "meta.*"],
  "need_structure": true,
  "page_no": 1,
  "page_size": 50
}
```

如果需要从子任务类型反查父 Story，使用 MQL 的子任务父工作项固定写法：

```sql
SELECT `工作项ID`, `名称`, relation_field_chain('__父工作项')
FROM `cem`.`sub_task`
WHERE any_relation_match(relation_field_chain('__父工作项'), x -> x.`工作项ID<target:all>` = '<story_id>')
```

当前固定口径优先使用 Task 对 Story 的关联字段反查：

```sql
SELECT `工作项ID`, `名称`, `关联 Story`, `职务类型`, `预估时间（h）`, `实际工作时间（h）`, `状态`
FROM `cem`.`65f98267c45577d0d95ea17b`
WHERE any_match(`关联 Story`, x -> x in ('<story_id_1>', '<story_id_2>'))
```

当前空间中的“开发任务 Task”工作项类型 key 为 `65f98267c45577d0d95ea17b`；不要误用系统内置 `sub_task`，否则 MQL 会出现字段 label 找不到。

如果 MQL 返回的 task ID 为空或为 `0`，不要自行生成 task ID；明细中展示 task 名称、岗位、预估、实际和状态，并在缺失记录中说明 task ID 不可用。

## 工时字段取值

### 预估耗时

按优先级读取：

1. 子任务排期估分：`points`、`schedule_point`、`schedule_point_value`。
2. WBS 行估分：`base.schedule` 或 `update_schedule_points` 对应字段。
3. 节点/任务字段中的“预估耗时”“开发预估耗时”“估分”。

归一规则：

| 单位 | 小时折算 |
|---|---:|
| 小时 | 原值 |
| 天 | `值 * hours_per_day` |
| 周 | `值 * 5 * hours_per_day` |
| 未知 | 保留原值并标注“单位未知” |

### 实际耗时

按优先级读取：

1. `get_workitem_man_hour_records` 返回的工时登记记录。
2. WBS 行实际工时：`actual_time`、`schedule_actual_times` 等字段。
3. task 字段中的“实际耗时”“实际工时”。

同一 task 多条工时记录要累加；同一人员多次登记不去重。

如果 Task 查询或工时字段读取报错，保留已成功获取的上游 feedback/Story 数据，并在对应行标记“Task 查询失败”或“工时查询失败”；不要用历史工时、人员经验或任务名称估算工时。

研发组开发自测时间只有在存在明确 task、字段或工时记录时才统计；没有明确记录时必须在报告中标注“研发组开发自测时间缺少明确记录未统计”。

### 证据记录

每条进入正式合计的数据都要生成证据记录：

| 字段 | 说明 |
|---|---|
| `evidence_id` | 报告内唯一 ID，如 `EV-FB-001`、`EV-HOUR-023` |
| `source_type` | view、workitem_field、man_hour_record、mql、operation_record、wbs_row |
| `source_locator` | 视图 ID、工作项 ID、Task ID、工时记录 ID 或查询参数摘要 |
| `raw_value` | 原始字段值或原始工时值 |
| `normalized_value` | 归一后的小时、人天、状态或文本 |
| `collected_at` | 查询或整理时间 |
| `used_in` | 被哪些汇总指标、leader 摘要或风险项引用 |

无法生成证据记录的数据只能进入“数据缺失与报错记录”，不得进入 leader 摘要、资源投放总览和正式合计。

## 分类规则

按顺序判定，命中即停止：

| 分类 | 优先匹配来源 | 关键词 |
|---|---|---|
| 前端 | 角色、负责人组、节点、任务名 | `前端`、`FE`、`Frontend`、`Web`、`H5` |
| 后端 | 角色、负责人组、节点、任务名 | `后端`、`BE`、`Backend`、`Server`、`RD` |
| 测试 | 角色、负责人组、节点、任务名 | `测试`、`QA`、`Test`、`验收` |

无法分类时输出“未归类”。不要用人员姓名硬编码分类，除非用户提供团队成员映射。

组别统计：

| 组别 | 包含分类 | 说明 |
|---|---|---|
| 研发组 | 前端、后端 | 按前端 1 人、后端 1 人计算可用人天 |
| 测试组 | 测试 | 测试为灵活借用资源，单独统计借用投入 |

## 汇总口径

### Leader 汇报口径

报告首屏必须服务 leader 决策，先给结论，再给证据入口：

| 模块 | 必须回答的问题 | 证据要求 |
|---|---|---|
| 资源投放总览 | 统计区间内研发小组投入了多少小时/人天 | 可追溯到成员、Task、工时记录或实际工时字段 |
| 消耗结构 | 资源主要消耗在哪些 feedback、Story、岗位和成员上 | 可追溯到 feedback ID、Story ID、Task ID/名称 |
| 投入产出 | 哪些投入已形成客户声音、上线、Story 完成或任务完成等产出证据 | 只使用飞书项目字段事实，不编造价值分 |
| 偏差风险 | 哪些 feedback 实际耗时高于预估、无客户声音、无 Story/Task 或工时缺失 | 明确缺失字段、失败工具和未纳入合计的数据 |
| 管理建议 | 下一步资源调整、补录客户声音、补齐工时或拆分 Story 的建议 | 建议必须来自前述事实，不输出无依据判断 |

Leader 摘要生成规则：

- 每条结论必须引用证据入口，证据入口可以是证据 ID、表格行锚点或工作项 ID 列表。
- 每个比例必须展示分子、分母和覆盖范围，例如“12/20，覆盖回收统计全集”。
- 查询失败或字段缺失影响结论时，结论必须降级为“可观察事实”，不能写成确定性判断。
- 不输出“效果显著”“价值较高”“收益明显”等无字段支撑的判断。

### 成员维度

如果输入包含 `team_members`，成员维度只统计名单内成员，名单外投入进入“非小组成员/借用投入”；如果没有输入名单，使用 Task 负责人、工时登记人和角色字段形成事实参与人清单。

成员维度必须包含：

- 成员姓名或 user_key。
- 岗位分类：前端、后端、测试、未归类。
- 参与 feedback 数、Story 数、Task 数。
- 预估耗时、实际耗时、实际人天。
- 主要投入 feedback Top 项。
- 证据来源：Task ID/名称、工时记录或字段来源。

### 单个 feedback

每个 feedback 的统计包含：

- `feedback_id`
- `feedback_name`
- `deploy_time`
- `customer_voice_status`
- `customer_voice_content`
- `customer_voice_updated_at`
- `output_evidence`
- `story_count`
- `task_count`
- `frontend_estimated_hours`
- `frontend_actual_hours`
- `backend_estimated_hours`
- `backend_actual_hours`
- `test_estimated_hours`
- `test_actual_hours`
- `uncategorized_estimated_hours`
- `uncategorized_actual_hours`
- `total_estimated_hours`
- `total_actual_hours`
- `member_actual_hours`
- `estimate_actual_delta_hours`
- `evidence_refs`

### 全局汇总

同时输出两个口径：

1. **按 feedback 累计**：同一个 Story/task 被多个 feedback 关联时，分别计入各自 feedback。
2. **去重累计**：按 task ID 去重；无 task ID 时按 `story_id + task_name + node_name` 去重。

如果本次数据没有发现共享 Story/task，报告只需输出单一汇总，并在缺失记录中说明未发现共享重复；不要强行添加空的去重汇总表。

### 客户声音回收汇总

必须输出：

| 指标 | 计算 |
|---|---|
| 回收统计全集总数 | 已填写数量 + 未填写数量 |
| 已填写客户声音数量 | 客户声音字段非空的 feedback 数 |
| 未填写客户声音数量 | 客户声音字段为空的 feedback 数 |
| 客户声音填写率 | 已填写数量 / 回收统计全集总数 |
| 本周新增填写数量 | 统计周内客户声音字段 create/modify 命中的 feedback 数 |
| 超 30 天未填写数量 | 未填写集合中上线超过 30 天的 feedback 数 |

如果回收统计使用主集合而不是独立视图，指标名称加上“主集合”；不要暗示其代表全局已上线回收率。

### 精要统计卡片

维度宽表上方必须输出精要统计卡片：

| 指标 | 计算 |
|---|---|
| 总实际耗时 | 前端实际 + 后端实际 + 测试实际 + 未归类实际 |
| 总预估耗时 | 前端预估 + 后端预估 + 测试预估 + 未归类预估 |
| 平均每个 feedback 实际耗时 | 总实际耗时 / feedback 数 |
| 平均每个 feedback 预估耗时 | 总预估耗时 / feedback 数 |
| 实际人天投入成本 | 总实际耗时换算为人天，仅输出数值 |
| 预估人天投入成本 | 总预估耗时换算为人天，仅输出数值 |
| 统计区间工作日 | 按用户给定区间和中国调休日历计算 |
| 研发组实际投入 | 前端实际 + 后端实际，同时输出小时与人天 |
| 研发组可用人天 | 工作日 * 2 人 |
| 研发组投入占比 | 研发组实际人天 / 研发组可用人天 |
| 测试组实际借用投入 | 测试实际，同时输出小时与人天 |
| 测试组预估借用投入 | 测试预估，同时输出小时与人天 |
| 实际/预估偏差 | 总实际耗时 - 总预估耗时 |
| 投入最高 feedback | 按实际耗时排序的 Top feedback |
| 无产出证据但有投入 | 有工时但无客户声音、Story 状态或上线证据的 feedback 数 |

不要在卡片中解释人天换算公式；只有用户追问时再解释。

### 风险识别

默认风险类型：

| 风险类型 | 触发条件 | 输出要求 |
|---|---|---|
| 超预估 | 实际耗时 / 预估耗时 >= `estimate_overrun_ratio`，默认 1.2 | 展示 feedback、Task、偏差小时和证据 ID |
| 高投入无客户声音 | 实际耗时 >= `high_investment_hours` 且客户声音为空 | 展示投入小时、客户声音状态和负责人 |
| 高投入无完成证据 | 实际耗时 >= `high_investment_hours` 且 Story/Task 状态无完成或上线证据 | 展示状态字段原值 |
| 工时缺失 | 有 Task 但实际工时字段和工时记录均为空 | 不纳入实际合计，列入补录建议 |
| 非小组成员投入 | 成员不在 `team_members` 内 | 单独计入借用/外部投入 |
| 未归类岗位 | 无法归入前端、后端、测试 | 保留未归类，不并入研发组或测试组 |

风险建议必须来自风险类型和证据，不允许输出泛化建议。

## 失败处理矩阵

| 失败点 | 处理 |
|---|---|
| `get_view_detail` 报错 | 停止统计，输出工具名、参数、原始错误 |
| 客户声音回收独立视图报错 | 记录错误；可退回主集合计算局部回收率，但必须标注覆盖范围 |
| 客户声音字段缺失 | 研发投入继续统计；客户声音列输出“字段缺失”，回收率标注无法按字段判定 |
| 操作记录查询失败 | 不输出伪填写时间；保留客户声音内容并记录无法判定本周新增 |
| 视图字段缺失 Story 关联 | feedback 保留，Story/Task 计 0，缺失记录标注 |
| MQL 报错 | 保留 feedback/Story，Task 计 0，输出 MQL 和原始错误 |
| Task 工时字段为空 | 空值按 0 统计，并在缺失记录标注 |
| Task 分类不在前端/后端/测试 | 进入未归类，不并入三类 |
| task ID 为空或为 0 | 不展示伪 ID，按 task 名称等信息追溯 |
| 成员不在小组名单 | 单独归为“非小组成员/借用投入”，不并入研发小组成员投入 |
| 汇总数字无法追溯 | 不纳入 leader 摘要和正式合计，只在缺失记录中说明 |
| 比例分母不一致 | 拆成多个指标分别输出，不做横向比较 |
| 风险缺少触发证据 | 不输出风险结论，只在待补充证据中列出 |
